# ADR 0001: V1 范围重排

- **状态：** Accepted
- **日期：** 2026-06-18
- **决策人：** 苏苏、Senior Developer、后端主程
- **影响范围：** 全部 7 人研发团队、未来 4 个月的工作节奏

## 背景与问题

原 FNAI 架构文档规划了 **14 个开发阶段、42 张数据库表、33 周开发周期**，包含完整的管理后台、GEO 模块、SERP 监控、A/B 测试、计费、流量分析等。

**问题：**
1. 团队规模仅 7 人，33 周（≈8 个月）超出大多数创业公司的可承受范围
2. 范围过大导致 V1 难以聚焦核心商业闭环
3. 多个模块（计费、A/B、GEO）属于 V2 阶段能力，提前做会拖累核心交付
4. 文档未明确"什么不做"，团队容易陷入范围蔓延

## 考虑的选项

### 选项 A：维持原计划，33 周交付

- 优点：一次到位，功能完整
- 缺点：周期过长，8 个月内无法上线验证；范围蔓延风险高

### 选项 B：砍半交付，V1 只做核心闭环

- 优点：4 个月内可上线；聚焦差异化能力（知识库 + 文章生成 + 发布）
- 缺点：客户无法在 V1 阶段使用精细化能力

### 选项 C：外包部分模块（如管理后台、计费）

- 优点：节省团队精力
- 缺点：增加沟通成本；7 人团队外部协调成本高

## 决策

**采用选项 B：V1 范围砍半，4 个月（16 周）交付核心商业闭环。**

具体范围参见 [`v1-scope-cut-list.md`](../../v1-scope-cut-list.md) 与 [`v1-development-phases.md`](../../v1-development-phases.md)。

## 理由

1. **验证优先**：AI 内容生成市场的核心价值是"内容质量 + 创作效率"，这两件事 V1 就能跑通
2. **资源匹配**：7 人团队 4 个月是务实估算，1 人月 1-2 个核心模块
3. **范围可控**：42 张表压到 22 张，砍掉 20 张 = 砍掉约 48% 的数据库复杂度
4. **可回滚**：V1.5 阶段再补齐任务中心、模型管理、计费，不影响核心

## 后果

### 正面

- V1 能在 2026 年 10 月底前灰度上线
- 团队节奏更清晰，每周都有明确目标
- 商业验证早 4 个月，能根据真实反馈调整方向
- 22 张表比 42 张更易维护

### 负面

- 客户无法在 V1 阶段使用计费、GEO、A/B 等能力
- 一些"如果不做 X 客户就不买"的反对意见需要应对
- V1.5 阶段工作量集中（再 3 个月）

### 风险与缓解

- **风险：客户拒绝 V1**
  - **缓解：** 用"邀请内测 + 折扣"换取 5-10 个种子客户的容忍
- **风险：团队有人想偷偷加功能**
  - **缓解：** 范围变更必须经苏苏审批；每条新需求都要砍掉等价工作量
- **风险：V1.5 工作量堆积**
  - **缓解：** V1 阶段就并行规划 V1.5；保留 1-2 人手准备 V1.5 模块

## 替代方案

- 32 周版本：保留管理后台 + 简易计费，但砍掉 GEO/SERP/A/B
- 已被否决：仍然超出 7 人 4 个月的可承受范围
